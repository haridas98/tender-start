# TenderStart: федеральный демо-фокус

## Решение

TenderStart показываем не как агрегатор тендеров и не как общий каталог заводов.

Формулировка демо:

**Промышленный deal intelligence cockpit: сырье -> подтвержденная потребность -> прямой производитель -> документы -> landed cost -> RFQ/сделка.**

## Главный риск

Нельзя уходить в ширину базы быстрее, чем в доказанность сделок. Для демо важнее 3-5 полностью собранных кейсов, чем тысячи lead-карточек.

## Демо-сценарий на завтра

1. Открыть `/demo`.
2. Показать кейс СНХЗ / глицидол.
3. Открыть `/plants/snhz`: завод, что производит, что закупает, кто отвечает, какие документы нужны.
4. Открыть `/materials/snhz-glycidol`: потребность, требования, документы, поставщики, пробелы в данных.
5. Открыть `/deals/snhz-glycidol-import-rfq`: RFQ-пакет, shortlist, документы, логистика, статусы проверки.
6. Показать будущий сценарий производителя: `/producer/register` и `/producers/demo-verified-chemical`.

## Что должно быть видно

- что подтверждено документом;
- что заявлено производителем;
- что является расчетом/оценкой;
- какие документы лежат внутри TenderStart;
- какой следующий коммерческий шаг;
- почему это не просто ссылка на внешний сайт.

## Страница производителя

Производитель должен иметь полноценную страницу:

- юридическое лицо и реестровые номера;
- производственные площадки;
- продукты: CAS, HS/ТН ВЭД, марка, чистота, упаковка, MOQ, мощность;
- COA/SDS/TDS/ISO/REACH/origin с локальным хранением и статусом проверки;
- Incoterms, порты, сроки, валюта, условия оплаты;
- публичные контакты sales/export/RFQ/quality;
- статус фактов: `заявлено`, `проверяется`, `подтверждено`.

## Ближайшие этапы

1. Сфокусировать UI на demo cockpit.
2. Сделать человеческие статусы качества вместо внутренних `lead/entity/source`.
3. Сделать producer registration/profile skeleton.
4. Переделать deal room в RFQ-доску.
5. Добавить документальную модель: source -> document blob -> extracted text -> fact -> verification status.
